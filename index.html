CH 1Introduction 導論

1.1 OS 是什麼

📌 定義 DEFINITION

Operating System 作業系統：介於使用者與硬體之間的程式，提供讓程式方便且有效率執行的環境。

  • resource allocator 資源分配者：管理 CPU、記憶體、I/O，處理資源爭用。
  • control program 控制程式：控制使用者程式的執行，避免錯誤或不當使用。
  • kernel 核心：「一直在電腦上執行的那個程式」，其餘是 system program 或 application program。
💡 例子 EXAMPLE

你在 Mac 上同時開 Safari 和 Spotify：OS 決定誰先用 CPU（resource allocator），並阻止 Safari 去改寫 Spotify 的記憶體（control program）。

1.2 OS 什麼時候會執行？（老師必講）

OS 平常是「睡著」的，只有在下列事件發生時才會拿到 CPU。這張表把 Ch1～Ch4 串起來：

#時機觸發來源例子

Modern OS 是 interrupt-driven 中斷驅動：沒有事件時 OS 什麼都不做；事件幾乎都透過 interrupt 或 trap 通知 OS。

開機流程 Bootstrap 🔥 考古 2017、2019 填空

📌 定義

bootstrap program 開機程式：存在 ROM / EEPROM / flash 中的第一個程式，initializes all aspects of the system, loads OS kernel, starts executing the OS（這句就是考古填空題的原文）。

// 開機流程
  1. 電源開啟，CPU 執行 ROM 中的 bootstrap programRAM 斷電後是空的，只有 ROM 的內容還在
  2. 初始化系統檢查並初始化 CPU 暫存器、記憶體、裝置控制器
  3. 載入 kernel image 到 RAM找到 OS kernel，複製到主記憶體
  4. 開始執行 OS，啟動第一個 process例如 UNIX 的 init / Linux 的 systemd
  5. 等待事件（interrupt）之後 OS 只在 interrupt / trap 發生時才執行

中斷處理流程 Interrupt Handling

  1. 裝置送出 interrupt 訊號給 CPU例如磁碟控制器完成讀取
  2. CPU 保存被中斷指令的位址與狀態這樣處理完才能回來繼續執行
  3. 查 interrupt vector 中斷向量表表中存著各種中斷對應的服務程式位址
  4. 跳到 ISR（interrupt service routine，中斷服務程式）執行此時處於 kernel mode
  5. 還原狀態，回到原程式繼續執行
🔗 關聯 DMA

DMA（Direct Memory Access，直接記憶體存取）：大量資料傳輸時，裝置控制器直接把整塊資料搬進記憶體，一整塊才發一次 interrupt，而不是每個 byte 都中斷 CPU。例：從 SSD 讀 1 GB 影片檔。

🔗 關聯與差異

trap 是大分類，system call 是「刻意的 trap」；exception（如 5/0）是「意外的 trap」。三者共同點：都會讓 CPU 從 user mode 切換到 kernel mode，交給 OS 處理。

1.4 Dual-Mode Operation 與 Timer 🔥 考古 每年必考

📌 定義

dual-mode operation 雙模式運作：硬體加上一個 mode bit，區分目前執行的是 OS 還是使用者程式。

  • kernel mode（mode bit = 0）：又稱 supervisor / system / privileged mode，執行 OS 程式碼。
  • user mode（mode bit = 1）：執行使用者程式。

privileged instruction 特權指令：可能造成危害、只能在 kernel mode 執行的指令（切換到 kernel mode、I/O 控制、timer 管理、中斷管理）。在 user mode 執行會被硬體 trap 給 OS。

// system call 的 mode 切換（考試畫圖題）
  1. user process 執行中（user mode，mode bit = 1）
  2. 呼叫 system call → 產生 trap硬體把 mode bit 設成 0，切到 kernel mode
  3. OS 查 system call table，執行對應的服務程式在 kernel mode 下可以使用 privileged instruction
  4. return from system callmode bit 設回 1，回到 user mode，程式繼續執行
📌 定義 Timer

timer 計時器：在指定時間後對 CPU 發出 interrupt，確保 OS 能拿回 CPU 控制權。OS 在把 CPU 交給程式前先設定 counter，每個 clock tick 遞減，歸零就產生 interrupt。設定 timer 是 privileged instruction。

⚡ 申論模板：為什麼需要硬體支援的 dual-mode？（用 trap、system call、timer 回答）
  • 目的：保護 OS 不被出錯的使用者破壞，也保護使用者彼此不互相破壞（protecting the OS from errant users, and errant users from one another）。
  • trap：程式做出非法動作（5/0、亂寫別人的記憶體、在 user mode 執行 privileged instruction）→ 硬體 trap 到 kernel mode，由 OS 處理（通常終止程式），錯誤不會擴散到 OS 和其他程式。
  • system call：使用者程式不能直接做 I/O 這類特權動作，只能透過 system call「請」OS 代做，OS 在 kernel mode 先檢查請求是否合法再執行 → 存取受控管。
  • timer interrupt：程式陷入 while(1){} 也不會霸佔 CPU；時間到 timer 中斷讓 OS 拿回控制權。而「修改 timer」是 privileged instruction，使用者程式無法關掉它。
  • 結論：只有 mode bit 由硬體維護，軟體才無法自行提權；若沒有硬體支援，任何程式都能執行特權指令，保護機制就形同虛設。
💡 例子

老師投影片的 4 個 Program Misbehavior：a=5/0（除零 exception）、b=(char*)0; b[10]='A'（寫入 NULL 附近，記憶體違規）、malloc(10) 卻寫 b[10000]（越界，可能 segmentation fault）、while(1){}（無窮迴圈 → 靠 timer 解決，不會產生 exception）。

🔗 延伸 Multimode

現代 CPU 不只兩種模式：Intel 64 有 4 個 protection rings；支援虛擬化的 CPU 另有 VMM mode，給 virtual machine manager 使用，權限介於 user 與 kernel 之間。

📌 定義

multiprocessor system：兩顆以上處理器，共用 bus、有時共用 clock、memory、周邊。主要優點是 increased throughput。

2.3 System Calls 系統呼叫

📌 定義

system call：提供使用者程式請 OS 代為執行 OS 工作的管道，是 OS 服務的程式介面。通常以 trap 的形式，跳到 interrupt vector 中特定位置。

API（Application Programming Interface）：程式設計師實際呼叫的函式（如 POSIX API、Windows API、Java API），API 內部再去呼叫 system call。

// printf("hi") 背後發生什麼事
  1. 程式呼叫 C 函式庫的 printf()API，仍在 user mode
  2. C library 呼叫 write() system call把 system call 編號放進暫存器
  3. 執行 trap（或 syscall）指令 → 切到 kernel modemode bit 0
  4. system call interface 依編號查表，呼叫 kernel 中的 write 實作把資料送到螢幕的 device driver
  5. 回傳狀態值，return 回 user modeprintf 回傳，程式繼續
🔗 API vs System call

為何不直接呼叫 system call？可攜性（portability）：同一份用 POSIX API 寫的程式可以在任何支援 POSIX 的系統編譯；另外 system call 細節比較複雜，API 比較好用。一個 API 不一定對應一個 system call（例如 abs() 根本不需要 system call）。

2.5 Linkers & Loaders、2.7 設計原則

  1. compiler 把 source code 編譯成 relocatable object filemain.c → main.o
  2. linker 把多個 object file 與函式庫合併成 executablemain.o + libc → a.out
  3. loader 把 executable 載入記憶體在 shell 輸入 ./a.out 時，shell 用 fork() + exec() 叫 loader 載入
  4. dynamically linked library（DLL / .so）在執行時才載入多個程式共用同一份函式庫
📌 Mechanism vs Policy

mechanism 機制決定「怎麼做」；policy 政策決定「做什麼」。兩者分開，改 policy 時不用改 mechanism，彈性較高。

💡 例子

timer 能中斷 CPU 是 mechanism；「每個使用者能用 CPU 多久」是 policy。Linux 的排程器提供機制，「I/O-bound 程式優先」則是政策。

2.6 為什麼 app 綁定 OS？因為每個 OS 的 system call、執行檔格式（ELF vs PE）、ABI 都不同。

Monolithic 架構

三大比較：extensibility、performance、security 🔥 2019 (12%)

面向monolithicmicrokernelLKM
extensibility 擴充性低：新增功能要改 kernel、重新編譯、重開機高：新增服務只要加一個 user-space 程式，kernel 不用改高：module 可單獨編譯，執行中載入/卸載，不用重開機

⚡ 一句話記憶

LKM 結合了 monolithic 的效能與 microkernel 的彈性（「while maintaining the performance benefits of a monolithic system」），但安全性不如 microkernel。投影片：LKM「Like the microkernel approach but is more efficient」、「similar to a layered system but more flexible（any module can call any other module）」。

💡 例子

插上新的 USB 網卡：Linux 用 insmod 載入驅動 module，不用重開機。Windows NT 早期是 layered microkernel，因效能太差，NT 4.0 把很多層搬回 kernel space，到 XP 已經比較接近 monolithic，這就是 microkernel 效能問題的真實案例。

⚠ 歷屆作答卷常見失分
  • 寫「microkernel 把常用功能放在 kernel mode 節省時間」→ 被扣分：microkernel 是把功能移出 kernel，目的不是省時間。
  • 寫「monolithic 一個出錯整個 process 暫停」→ 被扣分：應該是整個 kernel／整個系統受影響。
  • 寫 LKM 優點只寫「速度快」而沒寫原因 → 要寫出「不需 message passing」。

2.9 Building & Booting、2.10 Debugging

  1. BIOS 或 UEFI 韌體執行BIOS 舊式、多階段；UEFI 較新，單一完整的 boot manager，速度較快
  2. 載入 boot loader（如 GRUB）顯示開機選單，可選擇要開的 kernel
  3. 載入壓縮過的 kernel image 並解壓縮Linux 的 vmlinuz
  4. 掛載暫時的 root file system（initramfs）
  5. 切換到真正的 root file system，啟動 systemd第一個 process，之後啟動其他服務

Debugging：core dump（process 當掉時的記憶體快照）、crash dump（kernel 當掉）、performance tuning 工具（top、ps）、tracing 工具（strace、BCC/eBPF）。

📌 定義 PCB

PCB（Process Control Block，行程控制區塊，也叫 task control block）：OS 用來代表一個 process 的資料結構，存放：

  • process state、program counter（下一個要執行的指令位址）、CPU registers
  • CPU-scheduling information（priority、queue 指標）、memory-management information（base/limit register、page table）
  • accounting information（CPU 用量、PID）、I/O status information（已開啟檔案、分配到的裝置）

Linux 中 PCB 是 C 結構 task_struct。支援 thread 的系統，PCB 會擴充成存放每個 thread 的資訊（多個 PC）。

3.2 Process Scheduling 與 Context Switch 🔥 2017 填空、2019 (8%)

名詞說明
ready queue已在記憶體、準備好等 CPU 的 process 排隊處（通常是 linked list，串 PCB）
wait queue等待某事件（如 I/O 完成）的 process 排隊處，不同事件有不同 queue
CPU scheduler從 ready queue 選一個 process 給 CPU core，執行非常頻繁（至少每 100 ms 一次），必須很快
swapping中期排程：記憶體不夠時把 process 換出到磁碟（swap out），之後再換回（swap in），降低 degree of multiprogramming
📌 定義

context 行程的上下文：存在 PCB 裡的 process 狀態，包括 CPU registers 的值、process state、memory-management information。

context switch 內文切換：save the state of the old process and load the saved state of the new process（2017 填空原句）。

// Context switch 的步驟（P0 → P1）
  1. P0 執行中，發生 interrupt 或 system callCPU 進入 kernel mode，OS 取得控制權
  2. 把 P0 的 context 存進 PCB0program counter、registers、state 等
  3. 更新 P0 狀態並放入對應 queueready queue（time slice 用完）或 wait queue（等 I/O）
  4. CPU scheduler 從 ready queue 選出 P1
  5. 從 PCB1 載入 P1 的 context還原 registers、切換 memory-management 資訊（page table）
  6. 切回 user mode，跳到 P1 的 PC 繼續執行P0 此時處於 idle
⚡ 重要觀念

Context-switch time 是 pure overhead（純粹的額外負擔），切換期間系統沒做任何有用的事，一般需要幾 microseconds，速度高度依賴硬體支援（例如有些 CPU 提供多組暫存器，切換只要改指標）。

3.3 Operations on Processes：fork()、exec()、wait()

📌 定義
  • fork()：建立新的 child process，child 是 parent address space 的複本。回傳值：child 拿到 0，parent 拿到 child 的 PID，失敗回傳負值。
  • exec()（如 execlp()）：用新的程式取代目前 process 的記憶體內容，成功就不會返回。
  • wait()：parent 等待 child 結束。
  • exit()：結束 process，資源歸還 OS。
// Shell 執行一個指令（老師投影片的 shell 範例）
  1. shell 讀取指令，例如 ls
  2. 呼叫 fork() 複製出 child兩個 process 從 fork() 之後的下一行繼續跑
  3. child（pid == 0）呼叫 execlp("ls", ...)child 的記憶體被換成 ls 程式
  4. parent（pid > 0）呼叫 wait()等 child 執行完
  5. child 執行完 exit()，parent 從 wait 返回shell 印出下一個提示字元
⚡ fork() 輸出題必背規則
  • fork 之後 parent 和 child 有各自獨立的變數複本，child 改 value 不會影響 parent。
  • fork 之前的程式只執行一次；fork 之後、if 判斷之外的程式兩邊都會執行。
  • parent 有 wait(NULL) → child 的輸出一定先印完。
  • 同一 process 內的 thread 共享 global 變數（見 Ch4）。
名詞說明例子
zombie 殭屍行程child 已結束，但 parent 還沒呼叫 wait()，PCB 還留在 process tableparent 忘了 wait，ps 看到 <defunct>
orphan 孤兒行程parent 沒 wait 就先結束，child 還在跑Linux 會把它交給 init/systemd 收養
cascading terminationparent 結束時，OS 連同所有 child 一起終止部分系統不允許 orphan

3.4 IPC：Shared Memory vs Message Passing 🔥 每年必考

📌 定義

cooperating process 合作行程：會影響其他 process 或被影響的 process。合作的理由：information sharing、computation speedup、modularity。

IPC（Interprocess Communication，行程間通訊）：讓 cooperating processes 交換資料的機制，兩種基本模型：

  • shared memory：建立一塊共用記憶體區域，雙方直接讀寫該區域。
  • message passing：透過 OS 提供的 send() / receive() 交換訊息。

Producer-Consumer Problem 🔥 2017、2019、近年

📌 定義

producer-consumer problem 生產者–消費者問題：cooperating processes 的典型範例。producer 產生資料放進 buffer，consumer 從 buffer 取出使用。必須同步：buffer 滿時 producer 不能放，buffer 空時 consumer 不能拿。

  • unbounded buffer：buffer 大小無限制，producer 永遠能放，只有 consumer 可能要等。
  • bounded buffer：buffer 大小固定，兩邊都可能要等。
💡 例子

web server（producer）產生 HTML，browser（consumer）讀取；compiler 產生組合語言給 assembler 用。

// Shared-memory 解法（bounded buffer, circular array） #define BUFFER_SIZE 10 item buffer[BUFFER_SIZE]; int in = 0; // 下一個空位 int out = 0; // 第一個有資料的位置 /* Producer */ /* Consumer */ while (true) { while (true) { while (((in+1) % BUFFER_SIZE) == out) while (in == out) ; // full, 等待 ; // empty, 等待 buffer[in] = next_produced; next_consumed = buffer[out]; in = (in+1) % BUFFER_SIZE; out = (out+1) % BUFFER_SIZE; } }
⚡ 為什麼最多只能放 BUFFER_SIZE − 1 個？

空的條件是 in == out。如果允許放滿 10 個，in 會繞一圈回到 out，此時也是 in == out，無法分辨「全空」還是「全滿」，所以犧牲一格：(in+1) % SIZE == out 就算滿。

// Message-passing 解法 /* Producer */ /* Consumer */ while (true) { while (true) { /* produce next_produced */ receive(next_consumed); send(next_produced); /* consume next_consumed */ } }

4.2 Multicore Programming：Concurrency vs Parallelism 🔥 2019 (8%)

📌 定義

concurrency 並行：讓多個工作都有進展（make progress）。單核心時是 interleaved（交錯）執行。

parallelism 平行：同一時間真的執行多個工作，需要多核心。

⚡ 重要觀念

有 parallelism 一定有 concurrency，但有 concurrency 不一定有 parallelism。單核心 CPU 快速切換，提供平行的「錯覺」，是 concurrent 但不是 parallel。

比較data parallelism 資料平行task parallelism 任務平行
切分方式把同一份資料切塊分給各核心，每核心做相同運算把不同工作分給各核心，每個 thread 做不同運算
例子雙核心加總 array[N]：core0 加前半、core1 加後半thread A 加總、thread B 求乘積；producer thread / consumer thread

Multicore 程式設計 5 大挑戰：dividing activities（找出可平行的工作）、balance（工作量平均）、data splitting（資料切分）、data dependency（資料相依需同步）、testing and debugging（執行順序多變，難除錯）。

⚡ 申論：多執行緒程式在單核心上會比單執行緒快嗎？

可能會，前提是程式有 I/O 或會 block 的操作：一個 thread 等 I/O 時，另一個 thread 可以用 CPU，CPU 不會閒著，提升 responsiveness 與 throughput。
但如果是純 CPU 運算（CPU-bound），單核心上同一時間只有一個 thread 在跑，多執行緒反而多了建立與切換的 overhead，可能更慢。

在多處理器上會比單處理器快嗎？若使用 one-to-one 或 many-to-many 模型（kernel 能看到多個 thread），thread 可以分到不同 CPU 真正平行執行，所以會更快；但若是 many-to-one，kernel 只看到一個 thread，多 CPU 也沒用。

kernel thread 核心執行緒：由 OS 直接支援與管理，可被 kernel 排程到 CPU。Windows、Linux、macOS 都支援。

CH 5.1–5.2CPU Scheduling 基本觀念

5.1 CPU–I/O Burst Cycle 與 CPU Scheduler

📌 定義

CPU–I/O burst cycle：process 的執行由 CPU 執行（CPU burst） 與 等 I/O（I/O burst） 交替組成。

  • I/O-bound 程式：很多短的 CPU burst（例：文字編輯器、網頁瀏覽）。
  • CPU-bound 程式：少數長的 CPU burst（例：影片轉檔、科學計算）。

CPU scheduler：CPU 閒置時，從 ready queue 選一個 process 執行。ready queue 不一定是 FIFO，也可以是 priority queue、tree、無序 linked list。

💡 例子

CPU burst 長度分布（Fig 5.2）是指數型：大量短 burst、少量長 burst。這就是為什麼排程演算法通常偏好短工作，以及為什麼 multiprogramming 能大幅提升 CPU 使用率（大多數時間 process 在等 I/O）。

Preemptive vs Nonpreemptive、Dispatcher

CPU 排程決策可能發生在 process 的 4 種狀態轉換：

  1. running → waiting例如發出 I/O request、呼叫 wait()
  2. running → ready例如 interrupt（time slice 用完）
  3. waiting → ready例如 I/O 完成
  4. terminatesprocess 結束
⚡ 判斷規則

只在情況 1 和 4 排程 → nonpreemptive（cooperative）：process 自願放棄 CPU，別無選擇一定要選新的。
情況 2、3 也會排程 → preemptive：OS 可以強行把 CPU 搶走。

比較nonpreemptive 不可搶先preemptive 可搶先
CPU 何時釋放process 自己結束或進入 waiting 才釋放OS 可隨時中斷並收回 CPU
排程時機只有 1、41、2、3、4
回應性差：長工作會卡住其他人好，適合互動式系統
問題一個 process 可能霸佔 CPU存取共享資料時可能有 race condition，需要同步機制（Ch6）；kernel 設計要考慮在 system call 期間被搶先的情況
例子早期 Windows 3.x幾乎所有現代 OS：Windows、macOS、Linux、UNIX
📌 定義 Dispatcher

dispatcher 分派器：把 CPU 控制權交給 CPU scheduler 選出的 process 的模組。

dispatch latency 分派延遲：dispatcher 停止一個 process 並啟動另一個所花的時間，越短越好（每次 context switch 都會呼叫 dispatcher）。

// Dispatcher 的 3 個工作
  1. Switching context把舊 process 的狀態存到 PCB，載入新 process 的狀態
  2. Switching to user modemode bit 設回 1
  3. Jumping to the proper location in the user program跳到新 process 的 PC，從上次中斷的地方繼續執行
🔗 Scheduler vs Dispatcher

CPU scheduler 負責「選誰」（決策）；dispatcher 負責「把 CPU 交給它」（執行切換）。這也是 mechanism（dispatcher）vs policy（scheduler 演算法）分離的例子。

5.2 Scheduling Criteria 排程評估指標

指標中文定義目標例子
CPU utilizationCPU 使用率CPU 忙碌的比例最大化40%（輕載）～90%（重載）
throughput產出量單位時間完成的 process 數最大化長工作 1 個/小時；短交易 10 個/秒
turnaround time周轉時間從提交（submission）到完成（completion）的總時間，含等待記憶體、ready queue、CPU 執行、I/O最小化批次工作看這個
waiting time等待時間在 ready queue 中等待的總時間（不含 I/O 時間）最小化排程演算法唯一能直接影響的
response time回應時間從提交 request 到第一個回應產生的時間（是開始回應，不是輸出完成）最小化互動式系統看這個
⚡ 重要觀念
  • 排程演算法不影響程式執行或做 I/O 的時間，只影響在 ready queue 等待的時間。
  • 對互動式系統，比起平均 response time，降低 response time 的變異數（variance）更重要：穩定可預期比偶爾很快更好。
  • 若一個 process 只有一段 CPU burst 且沒有 I/O：turnaround time = waiting time + burst time。
💡 例子

P1 在時間 0 到達，前面排了 6 ms 的工作，P1 本身要跑 4 ms：waiting time = 6，turnaround time = 6 + 4 = 10，若 P1 一上 CPU 就輸出第一個字，response time = 6。

🔗 指標之間的取捨

提高 throughput（偏好短工作）可能讓長工作的 turnaround time 變很長；縮短 response time（頻繁切換）會增加 context switch overhead，反而降低 CPU utilization。

II. Questions（90%）

1. Give examples and describe the differences between trap, system call, and interrupt. Using trap, system call, and timer interrupt as examples to discuss why modern OS take advantage of hardware-supported dual-mode operation. (15%)
→ Interrupt / Trap / System call→ Dual-mode
參考答案

差異：interrupt 由硬體非同步產生（例：鍵盤輸入、I/O 完成）；trap 是軟體產生的中斷，由錯誤引起（例：除以 0、非法記憶體存取）；system call 是使用者程式刻意請 OS 服務，以 trap 的形式進入 kernel（例：fork()、read()）。

為何需要 dual-mode：用 mode bit（kernel 0 / user 1）區分 OS 與使用者程式，保護 OS 與其他程式。

  • trap：使用者程式出錯或在 user mode 執行 privileged instruction 時，硬體 trap 到 kernel mode 由 OS 處理，錯誤不會破壞 OS 或其他程式。
  • system call：I/O 等特權操作只能透過 system call 由 OS 在 kernel mode 檢查後代為執行，結束後切回 user mode。
  • timer interrupt：避免程式無窮迴圈霸佔 CPU，時間到 OS 一定能拿回控制權；設定 timer 是 privileged instruction，使用者無法關閉。

以上機制都依賴硬體維護的 mode bit，軟體無法自行切換，保護才可靠。

2. (a) Draw the diagram of a typical microkernel and describe the microkernel approach. (b) Describe the loadable kernel modules approach. (c) Compare microkernel and LKM in terms of extensibility, performance, and security. (24%)
→ 2.8 OS 結構比較
參考答案

(a) 畫出 Fig 2.15：user mode 有 Application、File System、Device Driver；kernel mode 的 microkernel 只有 IPC、memory management、CPU scheduling；元件之間以 messages 溝通。
Microkernel approach：把非必要元件從 kernel 移出，實作成在各自 address space 的 user-level 程式；kernel 主要提供 client 與各服務之間的 message passing 通訊（例：Mach、QNX）。

(b) LKM：kernel 只保留核心元件，其他服務（驅動程式、檔案系統）以 module 形式在開機或執行時動態載入；module 在 kernel space，有定義好的介面，任何 module 可直接呼叫其他 module（例：Linux insmod/rmmod）。

3. What is the producer-consumer problem? Discuss the strengths and weaknesses of two IPC models to solve it. Draw the diagram for each model. (16%)
→ IPC→ Producer-Consumer
參考答案

問題：producer 產生資料放進 buffer，consumer 從 buffer 取出；必須同步，buffer 滿時 producer 不能放、空時 consumer 不能拿。

Shared memory（圖：A、shared memory、B、kernel 上下堆疊，A/B 都指向共享區）：buffer 放在共享記憶體，用 in/out 指標實作 circular buffer。
優：速度快，建立後是一般記憶體存取，不需 kernel。缺：同步與保護由程式設計師負責；不易用在分散式系統。

Message passing（圖：A、B 與 kernel 中的 message queue m0…mn）：producer send()，consumer receive()，buffer 由 OS 提供。
優：不需處理寫入衝突，實作簡單；適合分散式環境。缺：每次都要 system call，kernel 介入，較慢。

4. Draw the diagram and describe the memory layout of a process. What is the context of a process? Describe the actions taken by a kernel to context-switch between processes. (12%)
→ Memory layout→ Context switch
參考答案

Memory layout（高位址到低位址）：stack（區域變數、參數、return address）→ free → heap（動態配置）→ data（global 變數）→ text（程式碼）。

Context：存在 PCB 中的 process 狀態，包括 CPU registers、program counter、process state、memory-management information。

Context switch：interrupt 或 system call 發生 → kernel 把舊 process 的 context 存進它的 PCB → 將其放入 ready/wait queue → scheduler 選出新 process → 從新 process 的 PCB 載入 context（含記憶體管理資訊）→ 切回 user mode 執行新 process。切換時間是 pure overhead。

5. One-to-one model: (a) Draw and describe it. (b) Can a multithreaded application perform better on a multiprocessor than on a single-processor system? (c) On a single processor, can multithreaded perform better than single-threaded? (11%)
→ Multithreading models→ Concurrency vs Parallelism
參考答案

(a) 每個 user thread 對應一個 kernel thread（畫 4 條平行線連接 user space 與 kernel space）。一個 thread block 時其他仍可執行；可在多處理器平行；缺點是建立 user thread 就要建立 kernel thread，數量過多影響效能。Linux、Windows 採用。

(b) 可以。one-to-one 中每個 thread 都是 kernel 可排程的單位，可分配到不同 CPU 真正平行執行（parallelism），所以比單處理器快。

(c) 視情況。若程式有 I/O 或 blocking 操作，一個 thread 等待時另一個可使用 CPU，提升效能與回應性（concurrency）。若是純 CPU-bound 運算，單處理器一次只能跑一個 thread，多執行緒反而增加建立與切換的 overhead，不會更快。

1. What is dual-mode operation? Using trap, system call, and timer interrupt as examples to discuss why modern OS take advantage of hardware-supported dual-mode operation. (13%)
→ Dual-mode 申論模板
參考答案

Dual-mode：硬體提供 mode bit 區分 kernel mode（0）與 user mode（1）；interrupt / trap / system call 發生時切到 kernel mode 執行 OS 程式，完成後切回 user mode。privileged instruction 只能在 kernel mode 執行。

trap、system call、timer 的論述同 2019 第 1 題：trap 攔截錯誤與非法指令、system call 讓特權操作必須經過 OS 檢查、timer 防止程式霸佔 CPU。

2. Describe the microkernel and the modular kernel approach in OS design. Compare their strengths and weaknesses in terms of extensibility. (16%)
→ 2.8 OS 結構比較
參考答案

Microkernel：只把最小必要功能（process / memory 管理、IPC）留在 kernel，其他服務以 user-level process 執行，透過 message passing 溝通。
Modular（LKM）：核心元件在 kernel，其他服務以 module 動態連結進 kernel。

Extensibility 比較：兩者都容易擴充。microkernel 新增服務只要在 user space 加一個 server process，kernel 不必修改，且新服務出錯不影響 kernel（擴充較安全）；但新服務與他人溝通都要透過 message passing，擴充越多 overhead 越大。LKM 新增 module 不用重新編譯 kernel、不用重開機即可載入，且 module 間直接呼叫、效率高；但新加入的 module 在 kernel mode 執行，若有 bug 會危害整個系統。

4. What is the one-to-one multithreading model? Discuss its strengths and weaknesses. (8%)
→ Multithreading models
參考答案

每個 user thread 對應一個 kernel thread。
優點：比 many-to-one 有更好的 concurrency，一個 thread 呼叫 blocking system call 時其他 thread 仍可執行；多個 thread 可在多處理器上平行執行。
缺點：每建立一個 user thread 就要建立對應的 kernel thread，開銷大，kernel thread 太多會拖累系統效能，因此系統通常限制 thread 數量。
